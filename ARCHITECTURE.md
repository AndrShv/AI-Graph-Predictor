# AI Graph Predictor — архитектура

Гибридный сервис: принимает скриншот финансового графика и промпт, оцифровывает данные, строит прогноз и рисует его поверх оригинала. Python отвечает за ML и вычисления, Java (позже) за продуктовую часть.

---

## 1. Вывод по модели Qwen2.5-VL 3B

Как единственный «оцифровщик» модель **нереалистична**. VLM хорошо читает текст на картинке (заголовок, легенда, метки осей), но плохо измеряет геометрию: где бар, какая цена, какой пиксель. Дообучение улучшит формат ответа и чтение шкал, но не научит 3B-модель выдавать ~90 точных координат.

Идея реалистична, если разделить роли: **точные числа считает код, VLM описывает и объясняет**.

Что показал первый тест (график с OHLC-барами):
- В JSON попали числа из легенды (O/H/L/C, значения MA), но подставлены не по смыслу.
- Нет исторических точек и нет `pixel_x` / `pixel_y`.
- Даты выдуманы, прогноз противоречит собственному анализу, `confidence` взят из воздуха.

## 2. Гибридный пайплайн

1. **Препроцессинг** — валидация картинки, нормализация размера, определение типа графика (свечи, бары, линия).
2. **Калибровка осей** — OCR меток осей Y и X, линейное соответствие «пиксель → цена» и «пиксель → время». От него зависит вся точность.
3. **Оцифровка (OpenCV)** — выделение баров, свечей или линии по цвету и контурам. Результат: плотный массив `{timestamp, open, high, low, close, pixel_x, pixel_y}`.
4. **Прогноз** — отдельный модуль по **числам** из шага 3 (классические модели временных рядов или бустинг). Промпт пользователя превращается в параметры: горизонт, сценарий.
5. **Рендеринг** — цена прогноза переводится обратно в пиксели через ту же калибровку, линия рисуется Pillow/OpenCV поверх оригинала.
6. **VLM-слой** — модель получает картинку **и уже извлечённые числа** и пишет текстовый разбор: тренд, поддержка, сопротивление, индикаторы. Здесь 3B справляется заметно лучше.

VLM также можно использовать для сверки: заголовок и таймфрейм из текста против результатов OCR.

## 3. Разделение Python и Java

Принцип: **Java владеет продуктом, Python владеет вычислениями.**

### Java-сервис (позже)
- Регистрация, JWT / OAuth2, пользователи
- Лимиты и биллинг
- История запросов, метаданные в своей БД
- Публичный API для клиентов
- Выдача ссылок на картинки
- Оркестрация задач

### Python ML-сервис
- Принимает задачу, выполняет пайплайн, возвращает результат
- **Не** имеет своей пользовательской БД и своей аутентификации

### Контракт между сервисами
- **Асинхронно через RabbitMQ:** Java кладёт сообщение (`task_id`, `file_key`, промпт, параметры), Python-воркер забирает и публикует результат в другую очередь или обновляет статус.
- **Версионируемая JSON-схема** (`schema_version: 1`). Фиксируется первой и хранится отдельно, чтобы обе стороны её использовали.
- **Картинки по очереди не передавать.** Только ключ в MinIO / R2.
- У каждой задачи `task_id`, статусы `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`.
- **Идемпотентность:** повторная доставка того же сообщения не должна дублировать результат.
- Синхронный HTTP допустим для лёгких быстрых вызовов, тяжёлое всегда через очередь.

### Хранение
Один владелец записи на каждую сущность. Пользователей и историю пишет Java, Python возвращает результат (JSON + ключ итоговой картинки). Если Python пишет в общую БД напрямую, схема таблиц превращается в скрытый контракт, и это больно ломается.

## 4. План работ по порядку

1. Зафиксировать выходной JSON-контракт (точки, прогноз, анализ, ключ картинки, версия схемы).
2. Собрать генератор синтетических графиков (matplotlib) с известными истинными данными. Это тестовый набор с ground truth.
3. Написать CV-оцифровщик для одного стиля графика и измерять ошибку (MAE по цене, доля найденных баров). Другие стили добавлять потом.
4. Подключить прогноз и рендеринг.
5. Подключить VLM для текстового анализа поверх готовых чисел.
6. Только потом думать о дообучении и о Java. Нужно ли дообучение, решат метрики из шага 3.

## 5. Риски

- **Разнообразие графиков:** разные платформы, тёмные и светлые темы, свечи или линии, индикаторы поверх цены. Начать с одного-двух стилей и явно заявить, что поддерживаются только они.
- **Качество прогноза:** предсказать рынок по истории цены трудно, результат скорее иллюстративный. Показывать дисклеймер и сценарии вместо «точного» прогноза.
- **Colab + ngrok:** подходит для разработки, не для продакшена (нестабильный URL, лимиты). Для продакшена нужен свой GPU-сервер или управляемый инференс.
- **`concurrency=1`:** подходит для тестов. Под нагрузкой тяжёлые VLM-задачи ограничивать и масштабировать отдельно от лёгких (CV, рендеринг).
- **Координаты после уменьшения картинки** относятся к уменьшенному изображению; нужен пересчёт в масштаб оригинала.

## 7. Заметки по текущей отладке

- URL модели задаётся в `proprts.env` (`QWEN2_5_VL_3B_INSTRUCT_URL`); в `environment:` compose эту переменную не дублировать.
- Подстановка `${VAR}` в compose читает только shell и файл `.env`, но не `env_file`.
- При ошибке `address already in use` на порту 5002 в Colab: Runtime → Restart session.
- Не хранить секреты (ngrok-токен, R2-ключи, `JWT_SECRET`) в коде и репозитории; перевыпустить те, что уже светились в чатах. `.env` и `proprts.env` добавить в `.gitignore`.
